## Slide 3. 연락 전 판단과 상담 후 기록

### 발표 시간

약 1분

### 발표 대본

현재 FC의 업무 흐름을 연락 전부터 상담 후까지 따라가 보겠습니다.

먼저 연락 전 단계입니다. 담당자 변경, 장기 미접촉, 갱신 임박과 연락 동의 같은 고객 신호가 여러 항목에 흩어져 있습니다. FC는 이 정보를 하나씩 확인해야 관리가 필요한 고객을 찾을 수 있습니다.

가운데는 판단과 상담 단계입니다. FC가 오늘 연락할 한 명을 직접 정하고, 왜 지금 연락해야 하는지와 어떤 내용을 말할지도 다시 정리합니다. 즉, 누구에게 연락할지뿐 아니라 선정 이유와 연락 맥락까지 FC의 판단에 의존합니다.

상담이 끝나면 두 번째 단절이 생깁니다. 통화 내용을 다시 요약하고 CRM에 옮겨 적은 뒤 후속 일정과 접촉 결과를 각각 정리해야 합니다.

결국 고객 선정 과정과 상담 기록 과정에서 업무 흐름이 두 번 끊기고, 두 구간 모두 FC의 수작업으로 남아 있습니다.

### 강조 문장

`고객 선정과 상담 기록에서 끊긴 두 지점을 하나의 흐름으로 연결하는 것이 저희의 문제 정의입니다.`

### 다음 장 연결

그래서 연락 전에는 행동할 한 명을 만들고, 상담 후에는 그 결과가 다음 업무로 이어지게 설계했습니다.

## Slide 4. 해결 목표

### 발표 시간

약 45초

### 발표 대본

1-pick Agent는 먼저 고객이 연락 가능한 상태인지 확인합니다. 연락 동의가 없거나 진행 중인 민원이 있으면 점수가 높아도 추천하지 않습니다.

그다음 연락 가능한 고객에게만 Rescue Score를 계산하고, 최고점 한 명을 선정합니다. 화면에는 점수만 표시하지 않고 어떤 데이터와 규칙으로 선정했는지도 함께 보여줍니다.

선정된 고객은 연락 단계로 이어지고, 상담이 끝나면 요약과 CRM 초안, 후속 일정 후보를 만듭니다.

따라서 결과는 한 명의 이름이 아니라 선정 이유와 다음 업무가 포함된 Action Card입니다.

### 보충 설명

데모의 김동양 고객은 90점입니다.

- FC 변경 후 11개월: 20점
- 최근 접촉 후 14개월: 30점
- 갱신일까지 32일: 25점
- 최근 6개월 내 상담 이력 없음: 15점

월 보험료 금액은 점수에 사용하지 않습니다.

### 다음 장 연결

이 과정을 한 Agent에게 모두 맡기지 않고 책임별로 나눴습니다.

## Slide 5. Agent Architecture & Loop

### 발표 시간

약 1분 30초

### 발표 대본

가운데의 Orchestrator Agent가 전체 업무 상태와 실행 순서를 관리합니다.

Orchestrator가 모든 판단을 직접 하는 구조는 아닙니다. 세 개의 전문 Agent를 순서대로 호출하고, 각 결과가 조건을 충족했을 때만 다음 단계로 넘깁니다.

첫 번째는 고객 선정 Agent입니다. 전체 고객에게 Eligibility를 먼저 적용하고, 통과한 고객에게만 규칙 기반 Rescue Score를 계산해 한 명을 선정합니다.

두 번째는 근거·안전 Agent입니다. 연락 문장을 공식 상품·약관 자료의 근거와 연결하고, 위협성 표현이나 과장, 근거 없는 단정을 검사합니다. Safety 결과가 `COMPLIANT`인 경우에만 연락 Tool을 실행할 수 있습니다.

세 번째는 상담 분석 Agent입니다. Transcript에서 고객의 니즈와 걱정, 후속 요청을 구조화합니다. 이 결과로 CRM 초안과 후속 일정 후보를 만들지만 곧바로 확정하지는 않습니다.

연락 이후에는 대화 분석, CRM 초안, 후속 일정이 이어집니다. 실행 결과와 FC의 수정·확인 정보는 같은 세션에 저장됩니다. 현재의 학습 루프는 모델을 즉시 재학습하는 기능이 아니라 다음 추천 개선에 사용할 피드백을 축적하는 단계입니다.

오른쪽 가드레일은 Agent의 실행 경계를 고정합니다. 근거 계약, Safety Gate, FC 확인 Gate, 상태 전이 검증과 중복 실행 방지가 이 역할을 합니다.

### 기술 강조 문장

`Agent는 판단 책임을 갖고, Tool은 계산·외부 실행·저장을 담당합니다.`

`Orchestrator는 상태를 건너뛰지 못하게 하고, 각 단계의 결과와 근거를 다음 단계로 전달합니다.`

### 상태 흐름 설명이 필요할 때

정상 흐름은 다음 순서입니다.

`POOL_SCAN → SCORING → PICK_READY → GROUNDING → SAFETY_CHECK → CONTACT_READY → TRANSCRIPT_READY → ANALYSIS → CRM_DRAFT → NEXT_ACTION → DONE`

Safety가 실패하면 실행하지 않고 `FEEDBACK` 상태로 보냅니다.

### 다음 장 연결

이 구조가 안정적으로 동작하려면 프롬프트뿐 아니라 프롬프트 바깥의 실행 통제가 필요합니다.

## Slide 6. 프롬프트·하네스·스킬

### 발표 시간

약 1분 25초

### 발표 대본

에이전트를 안정적으로 만들기 위해 세 가지 기술을 적용했습니다.

첫 번째는 프롬프트 설계입니다.

에이전트가 맡은 역할과 사용할 자료, 지켜야 할 규칙, 결과 형식을 따로 정했습니다. 답변도 자유롭게 쓰게 두지 않고 정해진 데이터 형식으로 만들었습니다. 그리고 모든 결과에 출처를 붙여, 왜 이런 결과가 나왔는지 확인할 수 있게 했습니다.

두 번째는 하네스입니다. 하네스는 에이전트가 정해진 범위 안에서만 움직이도록 통제하는 장치입니다.

실행 순서를 고정하고, 근거가 없거나 위험한 문장은 연락에 사용하지 못하게 막습니다. 상담 결과도 FC가 확인하기 전에는 CRM이나 일정에 확정하지 않습니다. 같은 요청이 반복되더라도 전화나 저장이 두 번 실행되지 않도록 처리했습니다.

세 번째는 업무 기능과 외부 연동을 분리한 것입니다.

슬라이드에서 말하는 스킬은 에이전트가 담당하는 독립된 업무 기능입니다. 고객 선정, 근거 확인, 상담 분석을 각각 나누어 만들었습니다. 전화와 문자, 음성 변환, CRM과 일정 등록은 별도의 연결부로 분리했습니다. 현재는 모의 기능을 사용하지만 실제 시스템을 연결할 때는 이 연결부만 바꿀 수 있습니다.

현재 버전은 실제 대형 언어 모델을 호출하지 않습니다. 점수 계산과 실행 순서처럼 결과가 항상 같아야 하는 부분은 규칙으로 구현했습니다. 앞으로 언어 모델을 연결하더라도 근거 확인, 위험 문장 차단과 FC 확인 절차는 그대로 유지합니다.

### 기술 강조 문장

`프롬프트는 결과를 만드는 방법을 정하고, 하네스는 그 결과를 실제로 사용해도 되는지 확인합니다.`

`현재는 모의 연동이지만, 실제 시스템으로 교체할 연결부는 분리해 두었습니다.`

### 다음 장 연결

이제 실제 화면에서 추천부터 후속 업무까지 연결되는 흐름을 보여드리겠습니다.

## Slide 7. 실제 화면 시연

### 권장 시연 시간

약 2분 30초

### 시연 시작 멘트

지금부터 한 고객을 선정하고 상담 결과가 다음 업무로 이어지는 과정을 보겠습니다.

### 시연 순서와 대본

#### 1. 오늘의 1-pick 실행

지금 전체 고객을 스캔합니다.

먼저 Eligibility를 확인하기 때문에 연락 동의가 없는 고객과 민원 진행 중인 고객은 추천 후보에서 제외됩니다. 연락 가능한 고객 중 Rescue Score가 가장 높은 김동양 고객이 90점으로 선정됐습니다.

점수 옆에는 FC 변경, 장기 미접촉, 갱신 시점과 상담 이력이라는 계산 근거가 표시됩니다.

#### 2. 연락 근거와 Safety 확인

이제 고객에게 연락할 이유와 채널별 스크립트를 확인합니다.

상품 관련 문장은 Knowledge 문서의 특정 근거와 연결되어 있습니다. Safety 결과가 `COMPLIANT`이므로 연락 실행이 가능합니다.

시간이 허용되면 다음 문장을 입력해 차단 흐름을 보여줍니다.

`지금 바꾸지 않으면 보장이 크게 줄어듭니다.`

이 문장은 `THREAT_PRESSURE`로 분류되고 `REJECTED` 처리됩니다. 이 경우 채널 Tool은 실행되지 않습니다.

#### 3. Mock 전화와 Transcript

전화 실행은 현재 실제 발신이 아니라 Mock입니다. 다만 전화 시작과 완료 상태, 시각과 실행 결과는 같은 Tool Contract로 기록됩니다.

준비된 Transcript를 불러오겠습니다. 실제 연동 환경에서는 이 자리에 STT 결과가 들어갑니다.

#### 4. 상담 분석과 CRM 초안

상담 분석 Agent가 고객 발화에서 기존 보장내용 점검 요청과 갱신 보험료에 대한 걱정, 후속 연락 희망 시간을 추출합니다.

각 항목에는 원문 발화 위치가 `TRANSCRIPT` 근거로 붙습니다. CRM 결과는 `DRAFT / FC_REVIEW`, 일정은 `PENDING_FC_CONFIRM` 상태로 시작합니다.

따라서 AI가 바로 저장하는 것이 아니라 FC가 내용을 확인한 뒤에만 Mock CRM과 Calendar Tool을 호출할 수 있습니다.

#### 5. 루프 종료

마지막으로 FC의 확인 또는 수정 내용과 실행 결과를 피드백으로 저장합니다.

이 데이터는 현재 온라인 학습에 직접 사용하지 않습니다. 다음 단계에서 추천 규칙과 모델을 개선할 수 있도록 동일 세션의 실행 이력으로 남깁니다.

### 시연 중 오류가 발생했을 때

데모 화면이 멈추면 다음처럼 설명합니다.

`현재 화면은 Mock Adapter를 사용하며, 핵심은 외부 API 호출 자체보다 Agent의 상태·근거·실행 Gate가 분리되어 있다는 점입니다. 다음 결과 화면을 기준으로 흐름을 이어서 설명드리겠습니다.`

### 다음 장 연결

이 흐름을 통해 처음 정의한 두 가지 pain point가 어떻게 바뀌었는지 정리하겠습니다.

첫 번째 pain point는 오늘 누구에게 연락할지 매번 직접 판단해야 한다는 점이었습니다.

1-pick Agent는 연락 가능 여부를 먼저 확인하고, 설명 가능한 규칙으로 고객 한 명과 선정 근거를 함께 제공합니다.

Agent는 Transcript를 구조화하고 CRM 초안과 후속 일정 후보를 만듭니다. FC의 확인을 실행 조건으로 두어 자동화와 통제도 함께 확보했습니다.

결국 1-pick Agent는 고객을 추천하는 기능에 그치지 않고, 추천을 실제 업무 완료와 다음 추천을 위한 피드백까지 연결합니다.

감사합니다.

### 마지막 한 문장

`1-pick Agent는 이유를 가진 한 명을 선정하고, 근거 있는 연락과 상담 이후 업무를 하나의 통제 가능한 루프로 연결합니다.`

# 예상 질문과 답변

## 1. 가장 가능성이 높은 기술 질문

### Q1. 실제로 LLM을 사용했나요?

현재 MVP의 실행 경로에서는 실제 LLM을 호출하지 않습니다. 고객 선정과 점수 계산, 상태 전이, Safety 검사는 규칙 기반 코드로 구현했습니다. Grounding은 Knowledge 문서의 키워드와 앵커를 사용하고, 상담 분석은 준비된 Transcript에서 규칙 기반으로 정보를 추출합니다.

저희가 구현한 핵심은 LLM 자체보다 LLM을 연결해도 유지할 출력·근거·실행 계약입니다. 실제 LLM은 향후 언어 생성과 의미 분석 영역에 연결할 예정입니다.

### Q2. LLM을 사용하지 않는데 왜 Agent라고 부르나요?

이 시스템은 단일 함수가 결과 하나를 반환하는 구조가 아니라, 고객 선정·근거 및 안전·상담 분석이라는 책임 단위가 독립되어 있고 Orchestrator가 상태에 따라 이들을 호출합니다.

다만 현재 각 Agent의 내부 판단은 재현 가능한 규칙 중심입니다. 따라서 정확한 표현은 `Agent 아키텍처를 구현한 결정론적 MVP`입니다. 이후 언어 판단이 필요한 부분만 LLM으로 교체해도 전체 실행 구조는 유지됩니다.

### Q3. Agent와 Tool의 차이는 무엇인가요?

Agent는 어떤 결과가 필요한지 판단하고 입력을 해석하는 책임을 가집니다. Tool은 점수 계산, 전화 상태 기록, CRM 저장처럼 정해진 작업을 수행합니다.

예를 들어 Customer Selection Agent가 고객 선정 과정을 책임지고, Rescue Score 계산기는 규칙을 실행하는 Tool 역할을 합니다. Orchestrator는 이 Agent와 Tool을 정해진 순서로 연결합니다.

### Q4. 왜 하나의 Agent가 아니라 여러 Agent로 나눴나요?

보험 상담에서는 선정 정확도, 상품 근거, 상담 내용 분석의 실패 원인과 통제 방법이 서로 다릅니다. 책임을 분리하면 각 Agent의 입력·출력과 실패 조건을 따로 검증할 수 있습니다.

또한 고객 선정 규칙만 변경하거나 Safety 정책만 강화할 때 다른 영역에 미치는 영향을 줄일 수 있습니다.

### Q5. Orchestrator는 구체적으로 무엇을 하나요?

Orchestrator는 상태 전이를 검사하고 전문 Agent를 호출하며, 각 단계의 결과와 근거를 수집합니다. 예를 들어 `PICK_READY` 이전에 Grounding으로 넘어가거나 Safety 검사를 건너뛰고 `CONTACT_READY`로 이동하는 흐름을 허용하지 않습니다.

정상 경로와 Safety 실패 경로를 분리하는 것도 Orchestrator의 역할입니다.

### Q6. 상태 머신을 사용한 이유는 무엇인가요?

LLM이나 외부 API의 결과만 믿으면 단계가 누락되거나 같은 작업이 반복될 수 있습니다. 상태 머신은 현재 단계에서 허용되는 다음 단계만 명시적으로 제한합니다.

덕분에 Safety 검사를 통과하지 않은 연락 실행, Transcript 없이 상담 분석, FC 확인 없는 확정 같은 잘못된 순서를 차단할 수 있습니다.

### Q7. 프롬프트 기법은 구체적으로 무엇인가요?

역할, 입력 데이터, 금지 조건, 출력 스키마를 분리하는 방식입니다. 출력은 자유 문장보다 JSON 구조를 우선하고, 각 결과에 근거 유형과 위치, 근거 문장을 함께 반환하도록 설계했습니다.

핵심은 Chain-of-Thought를 노출시키는 것이 아니라 검증 가능한 구조와 근거를 출력하게 만드는 것입니다. 모델의 내부 추론 대신 외부에서 확인할 수 있는 데이터와 규칙을 사용합니다.

### Q8. 하네스라는 말은 정확히 무엇을 의미하나요?

하네스는 Agent 주위에서 실행을 통제하는 코드와 계약의 묶음입니다.

이 프로젝트에서는 상태 머신, Evidence Contract, Tool Contract, Safety Gate, FC 확인 Gate, 실행 로그와 중복 실행 방지가 하네스에 해당합니다. 모델이 좋은 답을 만들었는지뿐 아니라 그 답을 실행해도 되는지 별도로 판단합니다.

### Q9. 여기서 스킬은 무엇인가요?

스킬은 Agent가 수행하는 업무 능력을 독립 모듈로 캡슐화한 단위입니다. 고객 선정, Knowledge 근거 연결, Safety 판단과 Transcript 분석이 각각의 스킬에 해당합니다.

특정 화면이나 외부 API에 종속되지 않도록 입력과 출력 계약을 기준으로 분리했습니다.

### Q10. 환각을 어떻게 막나요?

현재 구현은 공식 Knowledge 문서에 연결되는 문장만 허용하고, 결과에 `evidenceRef`와 `evidenceText`를 붙입니다. 근거가 없거나 금지 규칙에 해당하는 문장은 `REJECTED` 처리합니다.

다만 어떤 방식도 환각을 완전히 0으로 보장할 수는 없습니다. 실제 LLM 연결 시에도 검색 근거 제한, 구조화 출력 검증, Safety 규칙과 사람 확인을 함께 사용해야 합니다.

### Q11. Grounding은 RAG인가요?

현재는 임베딩 기반 RAG가 아닙니다. Markdown Knowledge 문서를 앵커 단위로 나누고 키워드로 근거를 찾아 문장과 연결합니다. MVP에서 결과 재현성과 출처 확인을 우선한 선택입니다.

향후 임베딩 검색이나 재순위화를 도입해도 최종 결과에 문서 위치와 원문을 붙이는 Evidence Contract는 유지합니다.

### Q12. Safety는 어떤 방식으로 검사하나요?

현재는 공식 판매 주의 문서에 정의한 규칙을 기반으로 위협·부추김, 근거 없는 단정, 과장 표현을 검사합니다. 결과는 `COMPLIANT` 또는 `REJECTED`이며, 실패하면 위반 유형과 근거를 반환합니다.

현재 규칙 기반 검사는 알려진 표현에 강하지만 문맥이 복잡한 변형 표현에는 한계가 있습니다. 운영 환경에서는 규칙, 분류 모델 또는 LLM 검토, 표본 감사와 정책 업데이트를 함께 적용해야 합니다.

### Q13. Safety를 통과하지 못하면 어떻게 되나요?

채널 Tool을 호출하지 않고 워크플로우를 `FEEDBACK` 상태로 보냅니다. FC가 문장을 수정하면 Grounding과 Safety를 다시 실행한 뒤 통과한 결과만 연락에 사용할 수 있습니다.

### Q14. Evidence Contract의 장점은 무엇인가요?

결과가 어느 데이터에서 나왔는지 추적할 수 있습니다.

- 고객 선정: `CUSTOMER_DATA`
- 상품 설명: `KNOWLEDGE_DOCUMENT`
- 상담 분석: `TRANSCRIPT`
- 실행 이력: `EXECUTION_LOG`

화면에서 근거를 보여줄 수 있고, 오류가 생겼을 때 어느 입력과 단계에서 발생했는지 감사할 수 있습니다.

### Q15. 왜 점수 계산을 LLM에 맡기지 않았나요?

고객 우선순위는 결과를 재현하고 설명할 수 있어야 합니다. 같은 데이터에 같은 점수가 나와야 하므로 규칙 기반 Tool이 적합합니다.

LLM은 연락 이유를 자연어로 설명하거나 상담 의미를 해석하는 등 언어 판단이 필요한 영역에 제한하는 것이 안전합니다.

### Q16. 90점은 어떻게 계산됐나요?

기준일은 데모 데이터에 고정된 2026년 9월 9일입니다. 김동양 고객은 FC 변경 후 11개월 20점, 최근 접촉 후 14개월 30점, 갱신일까지 32일 25점, 최근 6개월 내 상담 이력 없음 15점으로 총 90점입니다.

보험료 금액은 점수 계산에 사용하지 않습니다.

### Q17. 점수가 높은데 추천에서 제외되는 경우가 있나요?

있습니다. Eligibility를 점수보다 먼저 적용합니다. 연락 동의가 없거나 민원이 진행 중이면 `INELIGIBLE`로 분류하고 `rescue_score`를 부여하지 않습니다.

내부 설명용 `potential_score`가 높더라도 실제 추천 후보에는 들어가지 않습니다.

### Q18. 동점자가 나오면 어떻게 하나요?

현재 구현은 입력 순서에서 먼저 만난 최고점 고객을 선택합니다. MVP의 한계입니다.

운영 환경에서는 갱신 임박도, 마지막 접촉일, 고객 ID와 같은 명시적인 보조 정렬 규칙을 추가하고 그 규칙도 화면에 공개해야 합니다.

### Q19. FC 확인 Gate는 어디에 적용되나요?

CRM과 Calendar Tool에 적용됩니다. 상담 분석 결과는 먼저 `DRAFT / FC_REVIEW`와 `PENDING_FC_CONFIRM` 상태로 생성됩니다. `fc_confirmed=true`가 전달되지 않으면 저장 또는 일정 등록 Tool이 실행을 거부합니다.

### Q20. 중복 실행은 어떻게 막나요?

SQLite 실행 로그에서 `(session_id, event_type)`을 고유 키로 사용합니다. 같은 세션에서 같은 이벤트가 다시 요청되면 새로운 전화나 저장을 만들지 않고 기존 실행 결과를 반환합니다.

실제 외부 시스템을 연결할 때도 같은 값을 Idempotency Key로 전달하도록 확장할 수 있습니다.

## 2. 시스템 연동과 운영 질문

### Q21. 실제 전화나 CRM과 연동되어 있나요?

현재는 연동되어 있지 않습니다. 전화·문자·카카오톡·STT·CRM·Calendar는 Mock Adapter를 사용합니다.

대신 Agent가 특정 벤더 API를 직접 호출하지 않도록 `ChannelGateway`, `SttTool`, `CrmTool`, `CalendarTool` Interface를 정의했습니다. 실제 연동에서는 Interface를 구현하는 Adapter를 교체합니다.

### Q22. Mock인데 실제 연동 가능하다고 말할 수 있는 근거는 무엇인가요?

공통 입력과 `ToolExecutionResult` 출력 계약이 있고, 성공 여부, 실행 시각, 결과 참조, 오류 코드를 같은 형식으로 처리합니다. Safety와 FC 확인도 Adapter 앞에서 적용됩니다.

다만 인증, 벤더별 오류 처리, 네트워크 재시도와 운영 SLA는 실제 API 연결 단계에서 추가 검증이 필요합니다. 따라서 `연동 완료`가 아니라 `연동 가능한 계약과 Adapter 구조를 구현했다`고 설명합니다.

### Q23. 외부 API가 실패하면 어떻게 복구하나요?

현재 Mock 환경에서는 네트워크 실패를 구현하지 않았습니다. 운영 환경에서는 상태별 타임아웃, 제한된 재시도, 회로 차단, 실패 큐와 재개 가능한 워크플로우가 필요합니다.

상태 머신과 실행 로그가 있기 때문에 마지막 성공 상태 이후부터 재개하는 구조로 확장할 수 있습니다.

### Q24. 데이터는 어디에 저장하나요?

고객과 계약 Seed 데이터는 JSON, Knowledge는 Markdown으로 관리합니다. 실행 로그, 연락 시도, CRM Mock 기록, 일정과 피드백은 SQLite의 `data/runtime/demo.db`에 세션 단위로 저장합니다.

SQLite는 데모용입니다. 운영 환경에서는 권한 관리와 암호화, 백업과 감사 정책을 지원하는 데이터베이스로 교체해야 합니다.

### Q25. 개인정보 보호는 어떻게 하나요?

현재 데이터는 가상 고객을 사용합니다. 실제 개인정보 보호 체계까지 구현한 상태는 아닙니다.

운영 단계에서는 최소 수집, 필드 마스킹, 전송·저장 암호화, 역할 기반 접근 제어, 보존 기간, 감사 로그와 고객 동의 상태 동기화가 필요합니다. 특히 Transcript 접근 권한과 삭제 정책을 별도로 설계해야 합니다.

### Q26. 여러 FC와 많은 고객으로 확장할 수 있나요?

업무 책임과 Adapter가 분리되어 있어 구조적 확장은 가능합니다. 다만 현재 Streamlit과 SQLite는 단일 데모에 적합합니다.

운영 규모에서는 FC·조직별 데이터 격리, 서버형 데이터베이스, 작업 큐, 동시성 제어, 캐시와 모니터링을 추가해야 합니다.

### Q27. 실시간 상담 Copilot으로 확장할 수 있나요?

가능하지만 현재 범위에는 포함되지 않습니다. 실시간 STT, 부분 Transcript 처리, 낮은 지연 시간의 검색과 Safety, 상담 중 제안 UI가 추가로 필요합니다.

또한 실시간 제안과 통화 후 기록은 위험도가 다르므로 별도 권한과 검증 정책으로 분리하는 것이 적절합니다.

## 3. 품질·검증·비즈니스 질문

### Q28. 무엇을 검증했나요?

프로젝트의 기존 검증 기록에는 111개 자동 테스트 통과가 남아 있습니다. Eligibility 선행, 90점 재계산, Grounding 근거 연결, Safety 차단, 상태 전이, FC 확인 Gate와 중복 실행 방지를 검증했습니다.

발표에서는 `프로젝트 검증 기록 기준`이라고 표현하는 것이 정확합니다.

### Q29. 규칙 기반 점수에 편향이 생길 수 있지 않나요?

그럴 수 있습니다. 규칙 기반이라고 자동으로 공정한 것은 아닙니다. 다만 어떤 조건이 몇 점에 영향을 주는지 공개하고 감사할 수 있다는 장점이 있습니다.

운영 전에는 현업·준법 부서가 규칙을 승인하고, 고객군별 추천 분포와 실제 결과를 모니터링해야 합니다. 민감 정보가 점수에 불필요하게 들어가지 않는지도 확인해야 합니다.

### Q30. 추천 성능은 어떻게 평가할 계획인가요?

MVP는 기능 흐름과 안전 계약을 검증한 단계이며 실제 영업 성과를 측정하지 않았습니다.

운영 평가 지표로는 고객 선정 준비 시간, 연락 성공률, 상담 후 기록 시간, 후속 업무 누락률, FC 수정률과 고객 불만 발생률을 사용할 수 있습니다. 추천 모델을 개선할 때는 단순 계약 전환율만 최적화하지 않고 고객 관리 품질과 안전 지표를 함께 봐야 합니다.

### Q31. 피드백이 바로 모델 학습에 사용되나요?

아닙니다. 현재 Learn 단계는 FC의 행동, 수정한 초안, Safety 결과와 최종 실행 결과를 세션에 저장하는 단계입니다.

운영 환경에서는 이 데이터를 검수한 뒤 오프라인 평가와 규칙 개선에 사용해야 합니다. 검증 없이 온라인 학습에 바로 반영하면 잘못된 행동이 강화될 수 있습니다.

### Q32. 데모 기준일을 고정한 이유는 무엇인가요?

날짜가 바뀌면 경과 개월과 갱신 D-day가 달라져 점수가 달라집니다. 데모에서는 같은 입력에 같은 결과가 나오도록 기준일을 2026년 9월 9일로 고정했습니다.

실제 운영에서는 실행 시각을 데이터 스냅샷과 함께 저장해 나중에도 계산 결과를 재현할 수 있어야 합니다.

### Q33. 이 서비스의 가장 큰 기술적 차별점은 무엇인가요?

추천 모델 하나보다 추천 이후의 실행을 통제 가능한 루프로 연결한 점입니다.

선정 결과에 근거를 붙이고, Safety를 통과해야 연락할 수 있으며, 상담 분석 결과는 FC가 확인해야 저장됩니다. 모든 실행을 같은 세션과 계약으로 추적하기 때문에 결과를 설명하고 감사할 수 있습니다.

### Q34. 가장 큰 현재 한계는 무엇인가요?

실제 LLM과 외부 API를 연결하지 않았고, Grounding과 상담 분석도 규칙·키워드 중심이라는 점입니다. 데이터도 소규모 가상 Seed입니다.

따라서 현재 성과는 실제 영업 효과를 입증한 것이 아니라 Agent 책임 분리와 통제 구조가 end-to-end로 동작함을 보인 것입니다.

### Q35. 다음 개발 우선순위는 무엇인가요?

첫째, 실제 데이터 환경에서 규칙과 개인정보 통제를 검증해야 합니다. 둘째, Knowledge 검색을 고도화하고 언어 영역에 LLM을 제한적으로 연결해야 합니다. 셋째, 한 개의 실제 외부 시스템을 선택해 인증·오류·재시도까지 포함한 Adapter를 검증해야 합니다.

# 답변할 때 지켜야 할 표현

## 사용하면 좋은 표현

- `결정론적 Agent 아키텍처 MVP입니다.`
- `실제 연동이 아니라 연동 가능한 Interface와 Adapter 구조를 구현했습니다.`
- `현재 Learn은 모델 재학습이 아니라 피드백 데이터 저장 단계입니다.`
- `Safety와 Grounding이 위험을 줄이지만 완전한 무오류를 보장하지는 않습니다.`
- `CRM 초안과 일정 후보는 FC 확인 전에는 확정되지 않습니다.`
- `기존 프로젝트 검증 기록 기준으로 111개 자동 테스트를 통과했습니다.`

## 피해야 할 표현

- `실제 AI가 보험 상담을 자동으로 처리합니다.`
- `실제 전화와 CRM 연동을 완료했습니다.`
- `LLM이 고객 점수를 계산합니다.`
- `환각을 완전히 제거했습니다.`
- `상담 결과가 자동으로 CRM에 확정 저장됩니다.`
- `피드백으로 모델이 실시간 학습합니다.`

# 발표 직전 암기용 요약

## 문제

FC가 오늘 연락할 고객을 직접 판단하고, 상담 후 기록과 후속 업무도 다시 처리합니다.

## 해결

Eligibility를 먼저 확인한 뒤 Rescue Score로 한 명을 선정하고, 상담 결과를 CRM 초안과 후속 일정으로 연결합니다.

## Agent 구성

- Orchestrator: 상태와 호출 순서 관리
- 고객 선정 Agent: Eligibility, Score, 1-pick
- 근거·안전 Agent: Knowledge Grounding, Safety
- 상담 분석 Agent: Transcript, CRM Draft, Next Action

## 기술

- 구조화 JSON 출력 설계
- Evidence Contract
- 상태 머신
- Safety Gate
- FC 확인 Gate
- Tool Interface와 Mock Adapter
- SQLite 실행 로그와 Idempotency

## 현재 범위

실제 LLM과 외부 API는 연결하지 않았습니다. 규칙·키워드·Mock으로 통제 가능한 업무 루프를 구현했습니다.

## 마지막 문장

`1-pick Agent는 이유를 가진 한 명을 선정하고, 근거 있는 연락과 상담 이후 업무를 하나의 통제 가능한 루프로 연결합니다.`
